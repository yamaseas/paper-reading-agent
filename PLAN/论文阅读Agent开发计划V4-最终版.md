# Paper Reading Agent — 最终执行计划 V4

版本日期：2026-09-15。

本计划整合 V2 的阅读质量要求、V3 的简化架构，以及全页图片输入方案，作为后续开发依据。文中的配置值是初始工程默认值；阅读效果、实际用量和接口兼容性均须通过接入测试与校准确认。

## 1. 目标与范围

每天自动处理约 5 篇科研论文，为每篇生成完整的中文结构化阅读报告，覆盖问题、相关工作、方法、实验、局限与总结，并提供可回到原论文核查的证据位置。

以控制日常费用为明确约束，统一使用 `qwen3.8-flash`，围绕它完成输入优化和质量校准。通过补图、提示词与定向检查解决实际错误，未解决内容明确标记。

研究者阅读报告后自行选择 1–2 篇精读，可对任意论文追问，自行制作 slide。系统不替研究者决定哪些论文值得精读。

V1 包含：单篇阅读、页面与局部图像输入、证据定位、方法图、质量校准、五篇批处理和论文 Q&A。

V1 暂不包含：默认独立 Verifier、多模型路由、自动论文检索、自动 PPT、向量数据库、知识图谱、长期记忆，以及通用 Agent Framework。后续功能由实际错误与使用需求触发。

## 2. 冻结的架构决策

| 项目 | V1 决策 |
|---|---|
| 批处理 | 纯 Python，直接调用模型 API |
| 模型 | 固定使用 `qwen3.8-flash`，Reader、补图、格式修复和 Q&A 使用同一模型及服务端点 |
| API 客户端 | OpenAI Python SDK 连接阿里云兼容端点；不调用 OpenAI GPT 或 Anthropic Claude 原生 API |
| PDF 工具 | PyMuPDF，首先用于页面渲染和局部裁剪 |
| 主输入 | 每页一张图片，整篇图片按页序放入同一次主要请求 |
| 补充输入 | 必要页面或区域的更清晰图像，最多一轮自动补看 |
| 结构化产物 | `report.json`，作为报告、方法图、证据索引的唯一内容来源 |
| 展示产物 | Python 生成 `final.md` 和 Mermaid |
| Q&A | OpenCode 提供会话与工具调用，读取本地论文材料并访问页面图片 |
| 默认验证 | 本地结构检查 + 人工校准；是否增加模型 Verifier 由校准决定 |

阿里云当前视觉理解文档包含 Qwen3.8-Flash 的多图输入支持；具体端点上的图片输入、结构化输出与思考模式组合必须在 Phase 0 实测。[官方视觉理解文档](https://help.aliyun.com/en/model-studio/vision)

OpenCode 已提供非交互调用能力。本项目采用 Python 直连批处理，是为了控制固定流程的输入、输出、用量和恢复行为；OpenCode 主要承担多轮精读交互。[OpenCode CLI 文档](https://opencode.ai/v2/docs/cli/commands/)

```text
PDF
 ↓
PyMuPDF 自动逐页渲染 + 页码清单
 ↓
同一次主要请求：阅读要求 + 页码标签 + 全篇页面图片
 ↓
候选 report.json
 ↓
必要时：局部重渲染 → 一轮定向补看
 ↓
本地结构检查 → Markdown / Mermaid 渲染
 ↓
final.md + 原始页面 + 证据索引
 ↓
研究者阅读 / OpenCode Q&A / 自行制作 slide
```

## 3. 全页图片输入规则

### 3.1 自动渲染并一次提交

从原始 PDF 自动渲染图片，不手动逐页截图。每页保持独立文件，不把整篇拼成长图，也不把多页缩成拼图。

主要请求按顺序组织：

```text
阅读任务、输出 schema、论文 ID、PDF 总页数
PDF_PAGE=1 → page-001.png
PDF_PAGE=2 → page-002.png
...
PDF_PAGE=N → page-NNN.png
```

整篇图片共同进入上下文，生成一次完整阅读结果。V1 不采用“各页独立总结，再拼接摘要”，也不采用“每新增一页就重发此前所有图片并要求回复”。

默认覆盖输入 PDF 的全部页面，包括其中的参考文献和附录。外部补充材料只有在提供并纳入输入后才算已读取；报告注明材料覆盖范围。

官方支持一次请求传入多张图片，但仍受图片数量、文件大小和总输入 token 等限制。接入时按实际端点检查，不能只依据模型标称上下文长度判断能否发送。[多图输入与限制](https://help.aliyun.com/en/model-studio/vision)

### 3.2 清晰度与补看

初始渲染为 160 DPI、PNG。它是校准起点，不是所有论文都适用的清晰度保证。

需要重点观察：双栏小字、公式上下标、负号、表格行列对应、脚注、架构图箭头与模块标签。

模型返回 `visual_requests`，说明需要补看的 PDF 页码、原因，以及可选的区域坐标。Python 验证请求后，从原始 PDF 重渲染，初始采用 300 DPI；优先裁剪目标区域。整页坐标不确定时，可以提供该页或分栏图。

- 每篇最多一轮自动补看，最多 4 张补充图片。
- 区域坐标采用页面可见区域的归一化坐标 `[x0, y0, x1, y1]`，由渲染器统一处理页面旋转与尺寸映射。
- 越界页码、非法坐标或超出预算的请求不能直接执行；记录原因并保留未解决项。
- 补看请求携带候选报告、具体问题、相关原页及放大图；模型返回同一 schema 的完整修订报告。
- 修订只针对有新增证据的内容；保留前后版本以便核查。
- 补看后仍无法辨认的内容标记为“无法辨认/待核查”，不得填入猜测值。

API 可能按像素上限缩小图片，因此必须同时检查本地渲染尺寸与服务端图像设置。局部图可避免小字因整页缩放丢失；单纯提高 DPI 不保证模型看到更多细节。[高分辨率图像处理](https://help.aliyun.com/en/model-studio/vision)

### 3.3 文本与超限处理

主路径不依赖高质量 PDF→Markdown 转换。可选抽取带页码的粗文本，用于关键词定位、Q&A 找页及对照实验；不把粗文本默认当作准确原文。

PyMuPDF 的文本抽取仍可能存在多栏顺序问题，需要对照页面检查。[PyMuPDF 文档](https://pymupdf.readthedocs.io/en/latest/faq/index.html)

请求超过端点限制时，V1 停止该篇并记录 `input_over_limit`，不静默删页或截断输入后声称完成全文阅读。按章节分批阅读与全文综合属于后续扩展。

## 4. 页面与证据定位

`metadata.json` 保存 PDF 哈希、文件名、论文 ID、总页数和本次输入覆盖范围。

`pages.json` 保存每页的稳定 ID、从 1 开始的 PDF 页序、可获取的印刷页码、图片路径、渲染尺寸与参数。证据统一以 PDF 页序为主；印刷页码作为补充信息。

每条关键事实、方法节点和方法关系都必须引用证据 ID。证据至少包含：

| 字段 | 要求 |
|---|---|
| `id` | 本篇内唯一 |
| `pdf_page` | 对应真实输入页面，使用 1-based 页序 |
| `section` | 可辨认时填写，不能编造章节号 |
| `figure_or_table` | 相关图表编号，可为空 |
| `locator` | 段落、表格行列、图中模块等定位描述 |
| `quote` | 可清楚辨认时提供原文短摘录；无法读取时为空 |
| `image_id` | 对应原页或补充图像 |

表格数字同时记录指标、数据集、方法或 baseline、实验设置、单位和适用分母。只记录一个脱离上下文的数值不算完整证据。

Evidence Index 便于核查；页码存在、摘录存在都不能单独证明结论正确。图片中的摘录也是模型转录结果，需要在校准时对照原图。

## 5. Reader 内容要求

每篇报告开头展示标题、200–300 字中文摘要、输入覆盖情况和待核查事项。然后完整回答六问。

| 部分 | 必须覆盖 |
|---|---|
| Q1 解决什么问题 | 背景、已有不足、研究问题、动机、作者声称的贡献 |
| Q2 相关工作 | 最直接 prior work、baseline、与本文的具体区别；限定为已提供材料支持的内容 |
| Q3 方法 | 输入、输出、核心 insight、整体说明、结构化方法图、步骤表、实现细节 |
| Q4 实验 | 数据集、样本规模、baseline、模型、指标、实验设置、主结果、消融及论文提供的运行条件 |
| Q5 局限与展望 | 作者明确报告的局限和未来工作；Reader 分析单列 |
| Q6 完整总结 | 连贯说明问题、方法、结果、贡献及局限，避免简单重复摘要 |

Q4 优先按论文原始 RQ 组织；没有显式 RQ 时按实验目的组织，不编造作者的 RQ 编号。运行时间、硬件、trial count、网络访问等字段仅在适用且论文提供时填写。

所有事实与分析区分：`author_claim`、`reader_inference`、`llm_analysis`。报告中的自有分析展示为 `[LLM Analysis]`。

只有确认相关材料已读取、但作者未报告时才写 `Not reported`。材料缺失、页面未读或字迹不清分别标记，不与“未报告”混淆。

### 5.1 方法的五项产物

1. 1–3 段方法概述，解释输入、输出、核心思想和设计理由。
2. 结构化方法图，包含节点、关系与各自的证据 ID。
3. 由结构化数据生成的 Mermaid 图。
4. 方法步骤表：Step / Input / Operation / Tool or Model / Output / Why Needed / Evidence。
5. 关键实现细节：模型、prompt 或 agent 配置、分析工具、fuzzer、solver、检索、环境和重要超参，按论文实际内容填写。

方法关系必须说明是数据流、控制流或依赖；不能把排版顺序直接当作执行顺序。训练和推理流程必要时分开表达。

每个节点和每条关系都应有证据。无法从输入材料支持的关系进入待核查列表，不画成已确认关系；不能为了图形完整添加反馈环、隐藏步骤或他人方法。

对理论、综述或不适合流程图的论文，允许标记方法图不适用，并用适合的结构化说明替代，避免强行编造 pipeline。

## 6. 输出协议与确定性渲染

Reader 主调用与补看调用使用同一个报告 schema。根结构如下，详细字段在实现时定义于一个 `report.schema.json`：

```text
report.json
  schema_version
  paper_id
  title
  short_summary
  problem
  related_work[]
  method
    applicable / overview / inputs / outputs
    nodes[] / edges[] / steps[] / implementation_details[]
  experiments[]
  authors_limitations[]
  reader_analysis[]
  full_summary
  claims[]
  evidence[]
  visual_requests[]
  unresolved_items[]
```

报告字段中的关键断言引用 `claims`；claim 保存内容、观点归属与 `evidence_ids`。方法节点、关系和实验结果也直接引用对应证据 ID。摘要中的关键事实必须能追到相同的 claim。

Python 管理并附加输入清单、模型与 prompt 版本、运行和核查状态；这些状态不能由 Reader 自行宣布。

如果端点支持对应模式下的严格结构化输出，优先使用；否则使用 JSON 输出约束并在本地验证。schema 合法不等于语义正确。

本地检查包括：

- JSON 与 schema 是否有效，必需部分是否齐全，模型输出是否截断。
- 页码与图像 ID 是否属于输入材料，证据 ID 是否存在。
- 方法节点 ID 是否唯一，关系端点是否存在，节点与关系是否带证据引用。
- 关键结果是否保留单位、设置和必要的比较对象；缺失值不能自动填为 0。
- 图能否被 Mermaid 解析；报告中的文件链接是否正确。

Mermaid 使用稳定节点 ID、固定模板和安全标签转义，由 Python 生成。语法检查失败时修复渲染器或拒绝非法结构，不让模型通过增删方法关系来“修语法”。

`method.json` 和 `evidence.json` 可以作为派生文件导出，但它们必须来自最终通过结构检查的 `report.json`，不能独立编辑形成多个版本。

结构修复最多一次，仅用于格式问题。输出截断、缺失事实和证据矛盾不能作为纯格式错误处理。修复不能凭空补全内容。

## 7. 成功、失败与核查状态

每篇保留一个轻量 `job.json`，记录阶段、最近成功步骤、请求次数、运行指纹和产物路径，无需任务数据库或复杂调度框架。

| 输出状态 | 含义 |
|---|---|
| `done` | 输入覆盖完整，报告结构检查与渲染成功，无已识别的阻断项；不表示所有事实经过验证 |
| `needs_review` | 有可读报告，但存在未解决的关键证据、清晰度或内容问题，报告顶部列出 |
| `failed` | 输入超限、请求失败、输出截断或格式问题导致无法交付合格报告 |

事实核查另行记录：默认“未进行独立内容核查”；人工或模型核查后，记录核查方式、范围与发现的问题。不能把 `done` 或 Mermaid 可渲染展示为“事实已验证”。

## 8. 校准先于批处理扩展

### 8.1 第一轮：3–5 篇

选研究者已精读且能提供 PDF 的论文，覆盖双栏正文、复杂表格、方法图、公式或附录。ProtocolGuard、RFCAudit、CyberGym、SWE-bench 等可作为候选，以实际材料为准。

运行前从原文整理人工参考答案：问题与贡献、关键方法组件和关系、主实验结果及对应位置。不只凭熟悉程度或记忆评分。

首轮对照：

| 方案 | 输入 |
|---|---|
| A：默认方案 | 全篇页面图片 |
| B：对照方案 | 人工检查过的带页码文本 + 人工选定关键页面图片 |

保持相同模型、阅读要求、报告 schema 和评分规则，记录全部输入差异。对照组允许少量人工准备，不在这一阶段开发复杂 parser 或自动选图系统。

先比较一次主要调用的结果，再按相同补看规则统计最终结果，分别报告效果和开销。

### 8.2 指标与验收

| 指标 | 记录方式 |
|---|---|
| 问题与贡献正确性 | 逐项对照人工参考答案 |
| 关键组件召回 | 找到的正确关键组件 / 参考答案关键组件 |
| 方法关系精确率 | 有正确证据支持的生成关系 / 全部生成关系 |
| 关键关系召回 | 找到的正确关键关系 / 参考答案关键关系 |
| 主结果正确性 | 同时核对值、单位、数据集、设置和 baseline 对应关系 |
| 证据支持率 | 证据实际支持的被检查断言 / 全部被检查断言 |
| 严重错误 | 曲解核心结论、编造关键步骤、错误主结果等逐项计数 |
| 使用成本 | 输入、输出与缓存用量，补看与重试次数，耗时，人工纠错时间 |

分母为 0 的指标记为不适用，不能自动记为满分。

首轮进入批处理开发的目标：参考答案列出的核心问题、主要方法关系和主结果无未解决的严重错误；关键方法组件召回至少 90%；证据定位可复核。该门槛是项目初始验收要求，样本通过不代表对所有论文的准确率保证。

没有达到门槛时，按错误原因修复：

- 字看不清、表格漏读：先调整图像设置和局部补看。
- 文本或图片缺失：先修输入覆盖与预处理。
- 证据清楚但推理或归属错误：调整阅读约束，并评估定向 Verifier。
- 格式或链接错误：修 schema、校验器或渲染器。

全页图片达标且用量、耗时可接受时，保留 A 作为日常主路径。只有对照结果显示 B 有明确收益时才引入对应文本处理；输入方案变更必须记录依据。

### 8.3 扩展验收

正式日用前扩展至总计 10–20 篇，其中保留至少 3 篇不用于修改 prompt，进行独立验收。记录逐篇错误，不能让平均分掩盖严重失败。

## 9. Verifier 的增加条件

V1 不默认对每篇再读一遍。若校准发现证据清晰但 Reader 持续出现重要数字、方法关系或贡献归属错误，则评估定向验证。

第一轮只核查主结果、关键方法关系与主要贡献。Verifier 使用新 session，读取相应原页或放大图与待核查断言，输出支持、矛盾或无法判断及定位证据。

评估它纠正多少原有错误、漏掉多少、误改多少正确内容，以及增加的费用和耗时。可在原文依据明确的前提下人为修改少量数字、方向和 baseline 对应，测试检错能力。

同模型新 session 不保证错误独立。定向验证评估同样使用 `qwen3.8-flash`，只有验证带来可复现的净收益才加入默认流程。当前开发不安排模型升级或跨模型对比。

## 10. Q&A 交互方案

OpenCode 在对应论文工作目录中启动会话，初始获得报告、页码清单与材料路径，按问题读取相关页面。

接入时必须实测：图片文件或工具返回的图像内容确实进入模型视觉输入。仅提供图片路径字符串不算完成看图能力。

提供两个确定性工具：

- 读取任意 PDF 页面的图片，并返回该页身份信息。
- 从原始 PDF 按页和区域重渲染清晰图片，并返回可查看的图像。

粗文本可辅助关键词找页；相关页不明确时允许查看更多页面。V1 不需要向量库。

回答必须优先依据原论文，附 PDF 页码和必要的图表位置。`final.md` 是阅读笔记，不能作为证明自身正确的独立证据。论文没有报告的内容应明确说明。

默认按需发送页面，避免每次追问都重发全部图片。多轮上下文复用不等于免费，实际缓存命中和调用用量需要记录；官方缓存机制也不保证每次命中。[上下文缓存文档](https://docs.modelstudio.console.alibabacloud.com/en/model-studio/context-cache)

## 11. 批处理、日志与恢复

首轮开发和校准并发为 1；五篇批处理初始并发为 2，确认端点配额和稳定性后再考虑 3。并发单位是论文。

每次 API 调用立即记录事件和用量，不等整个批次结束才落盘。至少保存：

- 论文 ID、PDF 哈希、模型返回标识、prompt/schema/渲染配置版本。
- 调用类型、提供的页码和补图、输入输出及缓存 token；接口未提供的统计记为未知。
- 请求开始结束时间、耗时、重试、错误类型、结束原因。
- 原始响应、候选报告、补看前后版本、校验结果与最终状态。

API key 从环境变量读取，不进入日志；图像文件通过路径与哈希关联，不把整段 Base64 重复写进日志。

超时、限流和暂时性服务错误可退避重试；鉴权错误、输入超限或参数不支持应直接报告原因。每次逻辑调用最多重试 2 次，每篇最多实际发送 6 次请求，避免补看、格式修复和重试叠加失控。

渲染失败只重做渲染，Markdown 生成失败只重做本地输出；不能因本地步骤失败重新支付全文阅读费用。完成记录使用原子写入，避免半份报告被视为成功。

运行指纹至少包含 PDF、prompt、schema、模型配置与渲染参数。指纹相同且产物完整时可复用；配置变化产生新运行记录。

每日批次生成清单，列出每篇的报告入口、状态和待核查事项，便于发现失败论文。

## 12. 费用与性能记录

不预设全页图片一定比文本贵很多，也不预设补看或 Verifier 的成本固定翻倍，统一以实际 usage 和所用端点的 `qwen3.8-flash` 价格计算。

数量级参考：按官方当前图像 token 估算规则，A4 页面以约 160 DPI 渲染，每页约 2,400 个视觉 token；12 页约 2.9 万，每日 5 篇约 14.5 万。它仅估算主要调用的图像输入，未包括输出、提示词、补看、重试或 Q&A，实际以 API 返回为准。[官方图像 token 计算规则](https://help.aliyun.com/en/model-studio/vision)

首轮校准报告给出单篇与每日五篇的用量、费用和耗时，并记录适用的端点、区域与价格日期。价格缺失时输出 token 统计和“费用未知”，不能填 0。

## 15. 开发顺序与完成标准

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| Phase 0：单篇闭环 | 跑通 Qwen3.8-Flash 端点、多图输入、页码清单、Reader schema、本地检查、Q1–Q6 与 Mermaid；从首个调用保存日志 | 1 篇完整 PDF 得到可检查报告；无静默删页、截断或缺失产物 |
| Phase 1：补看与早期校准 | 接入有限补看，用 3–5 篇论文建立参考答案，比较全页图片与混合输入 | 达到第 8 节首轮门槛，明确输入方案、错误类型、费用和耗时 |
| Phase 2：按错误改进 | 修图像、prompt 或结构问题；必要时评估定向 Verifier | 已发现的严重错误完成修复或明确标记；新增机制有可核查收益 |
| Phase 3：批处理与 Q&A | 并发、退避、恢复、每日清单；OpenCode 实际看页与局部放大 | 5 篇分别得到报告或明确失败原因；失败不阻断其他论文；追问能引用原页 |
| Phase 4：日用验收 | 扩展至 10–20 篇，保留未参与调优的论文；检查质量和每日成本 | 无被成功状态掩盖的严重失败；独立验收结果支持日用 |

以下为待实现的 CLI 约定，开发完成后应可执行：

```bash
# 单篇开发与校准
python -m src.batch inbox/2026-09-15/paper.pdf --concurrency 1

# 每日批处理
python -m src.batch inbox/2026-09-15
```

必要测试集中在有实际失败风险的行为：页码与裁剪映射、非法引用、方法图转义、输出截断、重试上限、失败恢复，以及复制后链接。模型的阅读正确性通过人工参考答案评测，不能用 JSON 合法性测试代替。

## 16. 日常使用流程

1. 将约 5 篇 PDF 放入当天 inbox。
2. 执行批处理，查看每日清单中的完成、待核查和失败项。
3. 阅读每篇摘要与报告；必要时先核对待核查内容。
4. 自行决定精读论文，在 OpenCode 中追问并查看原页证据。
5. 自行制作 slide，记录发现的错误及对应原页，作为后续改进样例。

后续架构变更以这些真实错误、校准结果和使用记录为依据。当前第一项开发任务是完成一篇论文的全页图片阅读闭环。
